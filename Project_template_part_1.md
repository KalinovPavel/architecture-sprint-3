# Задание 1. Анализ и планирование

Чтобы составить документ с описанием текущей архитектуры приложения, можно часть информации взять из описания компании условия задания. Это нормально.

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в своих домах.
- Предполагается, что есть физические реле/устройства, позволяющие управлять котлами или другой отопительной техникой, связанными с системой.

**Мониторинг температуры:**

- Пользователи могут просматривать актуальную температуру в личном кабинете через веб-интерфейс.
- Система запрашивает данные о температуре с датчиков, установленных в домах.
  
### 2. Анализ архитектуры монолитного приложения

 - Язык программирования: Java
 - База данных: PostgreSQL
 - Архитектура: Монолитная
   - Все компоненты (REST-контроллеры, бизнес-логика, доступ к данным, интеграция с устройствами) находятся внутри одного приложения.
 - Взаимодействие: Синхронное
   - Запросы от пользователя и к внешним устройствам (датчикам и реле отопления) обрабатываются последовательно.
   - Нет механизмов событийной шины или асинхронного обмена сообщениями.
 - Масштабируемость: ограничена
   - Сложно масштабировать только отдельные модули по нагрузке, приходится поднимать/клонировать всё приложение целиком.
 - Развёртывание: монолит требует полной остановки при деплое новой версии.

Дополнительно:

 - У пользователей (веб-клиентов) всего ~100 активных сессий.
 - Подключено ~100 модулей управления отоплением.

### 3. Определение доменов и границы контекстов

1. Управление устройствами (Device Management)

   - Отвечает за подключение, регистрацию и конфигурацию устройств (датчики, реле отопления, умные лампы, приводы ворот и т. д.).
   - Граничный контекст в будущем может содержать микросервис для взаимодействия с устройствами (протоколы, сетевые шлюзы, настройки).

2. Контроль и мониторинг (Monitoring & Telemetry)

   - Домен отвечает за приём и обработку телеметрических данных (температура, состояние датчиков, состояния умных устройств).
   - В текущем монолите это реализовано простыми вызовами: «запросить температуру» → «вернуть ответ».

3. Управление отоплением (Heating Management)

   - Логика включения/выключения отопления, учёт температурных данных, работа с профилями пользователей, расписаниями и т. п.
   
4. Управление пользователями и доступом (User Management)

   - Регистрация пользователей, аутентификация/авторизация.
   - В монолите обычно это «вшито» в ядро приложения.
   - В будущем может быть вынесено в отдельный сервис управления идентификацией (IAM).

### **4. Проблемы монолитного решения**

Монолитное приложение не позволяет эффективно справиться с растущими потребностями компании «Тёплый дом» по следующим причинам:

1. Сложность расширения

   - Добавление новых возможностей (управление освещением, воротами, системой наблюдения и т. д.) приводит к изменению большого объёма кода и добавлению модулей в общий проект. Это увеличивает риски и время разработки.

2. Ограниченная масштабируемость

   - При росте числа пользователей и устройств нельзя эффективно масштабировать отдельные компоненты (например, только часть, отвечающую за телеметрию). Приходится клонировать весь монолит целиком.

3. Уязвимость при обновлениях

   - Любые правки кода требуют пересборки и выкатки всего приложения. Даже если нужно поправить логику работы только одного модуля, приходится перезапускать весь сервис.

4. Невозможность гибкого развития

   - Сложно интегрировать внешние партнёрские устройства и протоколы (новые датчики, камеры наблюдения, умные замки и пр.), так как всё завязано в общий код. Нет чётко выделенных контекстов и API.
     
5. Сложность распределенной разработки

   - Когда над системой работают несколько команд (разработка, DevOps, QA), монолит создаёт сложности в параллельной работе и тестировании.
